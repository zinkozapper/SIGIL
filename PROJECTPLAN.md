# Project SIGIL Plan

**Last updated:** 2026-10-11  
**Status:** Rails API, Android NFC client MVP, and first analytics dashboard are implemented; runtime and device verification are next.

## 1. Project purpose

SIGIL is a study-session system built around a physical tap event.

The first tap on the Google Pixel 9a starts the phone's study workflow. The second tap ends the workflow. After the session is complete, the Android client sends one complete session payload to the backend. The backend stores the session and later supplies data to the analytics dashboard.

The project is intentionally split into three components:

1. **SIGIL Client** — a small Android client for the Pixel 9a.
2. **SIGIL API** — a Rails backend that accepts and stores completed sessions.
3. **SIGIL Dashboard** — a future analytics frontend for reviewing study activity.

## 2. Design decisions

- Use Ruby on Rails for the backend and as a learning project.
- Use SQLite initially.
- Run the Rails application in Docker on the Docker host.
- Reach the backend from the phone through Tailscale.
- Let the phone cache unsent sessions locally when the server is unavailable.
- Synchronize cached sessions when connectivity returns.
- Send data only after a session is complete.
- Let Rails calculate authoritative session duration.
- Use a client-generated session ID for retry safety.
- Do not include a device table.
- Do not run automation on the backend.
- The backend stores successful completed-session submissions, not intermediate tap events.

## 3. Architecture

```text
Google Pixel 9a
SIGIL Client
  ├─ Tap 1: start local timer and study modes
  ├─ Tap 2: stop local timer and restore study modes
  ├─ Save completed payload in local outbox
  └─ POST payload to SIGIL API when reachable
             │
             │ Tailscale
             ▼
Docker host
SIGIL API — Rails
  ├─ Validate payload
  ├─ Calculate duration
  ├─ Ignore duplicate retries
  └─ Store StudySession in SQLite
             │
             ▼
SIGIL Dashboard — future analytics frontend
```

## 4. Database model

### `study_sessions`

| Column | Purpose |
|---|---|
| `id` | Rails primary key |
| `client_session_id` | UUID generated by the Android client; unique retry/idempotency key |
| `started_at` | When the study session began |
| `ended_at` | When the study session ended |
| `duration_seconds` | Calculated by Rails from the two timestamps |
| `subject` | Optional subject name |
| `chapter` | Optional chapter or reading location |
| `notes` | Optional free-form notes |
| `metadata` | Optional structured client information |
| `created_at` | Rails record creation time |
| `updated_at` | Rails record update time |

Required database rules:

- `client_session_id` is required and unique.
- `started_at` is required.
- `ended_at` is required.
- `duration_seconds` is required and non-negative.
- `ended_at` must be greater than or equal to `started_at`.

The database does not need `status`, `session_events`, `devices`, or separate start/end event IDs because only completed sessions are submitted.
